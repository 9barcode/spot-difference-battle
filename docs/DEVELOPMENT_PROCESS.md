# 개발 생명주기

> 문서 상태: CURRENT
> 기준일: 2026-08-31
> 책임 역할: 기술 책임자

모든 기능, 수정, 리팩터링, 에셋, 문서와 운영 변경은 아래 8단계를 따른다. 단계의 산출물과 게이트가 충족되지 않으면 다음 단계로 넘어가지 않는다.

## 0단계 — 요청 접수와 분류

**목적:** 해결할 문제와 긴급도를 명확히 한다.

- 사용자 문제, 재현 조건, 기대 결과를 한 문장으로 정의한다.
- 변경 유형과 위험도를 분류한다.
- 기존 백로그, 결정 기록과 중복 여부를 확인한다.
- 보안 사고나 운영 장애면 일반 개발이 아니라 장애 절차로 전환한다.

**산출물:** 이슈 또는 [변경 계약](templates/CHANGE_BRIEF.md)의 문제 정의

**통과 조건:** 해결할 문제, 대상 사용자, 성공 기준과 담당 역할이 식별됨

## 1단계 — 발견과 결정

**목적:** 구현 전에 의도와 제약을 확정한다.

- 정본, 코드, 데이터와 테스트의 현재 동작을 조사한다.
- 범위·비범위, 대안, 위험, 데이터·권리·운영 영향을 기록한다.
- 게임 규칙, 공개 범위, DB, 보안, 배포 또는 비용을 바꾸면 결정 기록을 작성한다.
- 결정권이 없거나 외부 확인이 필요하면 `REVIEW_REQUIRED.md`에 등록한다.

**산출물:** 변경 계약, 필요 시 결정 기록

**통과 조건:** 제품 책임자가 의도와 범위를 승인하고 미확정 전제가 없음

## 2단계 — 설계와 계획

**목적:** 요구사항이 코드·데이터·화면·테스트로 어떻게 이어지는지 정한다.

- 영향받는 요구사항 ID와 모듈을 연결한다.
- 상태 전이, API·이벤트·공유 타입, DB 마이그레이션과 UI 상태를 설계한다.
- 실패·재시도·취소·복구·롤백 경로를 포함한다.
- 필요한 자동·수동 테스트를 먼저 정한다.
- 작업을 독립적으로 검증 가능한 작은 단위로 나눈다.

**산출물:** 구현 계획, 명세 변경안, 테스트 계획, 롤백 계획

**통과 조건:** 기술 책임자와 관련 영역 책임자가 구현·검증·롤백 가능성을 승인함

## 3단계 — 구현

**목적:** 승인된 범위만 작고 추적 가능한 변경으로 구현한다.

- 정본과 파생 문서, 코드, 테스트를 같은 변경에서 갱신한다.
- 서버 권한과 정답 비공개 경계를 유지한다.
- 기존 사용자 변경과 무관한 리팩터링을 섞지 않는다.
- DB 변경은 전진 호환 순서로 적용하며 파괴적 단계는 분리한다.
- 에셋은 메타데이터, 해시, 권리와 QA 기록 없이 활성화하지 않는다.

**산출물:** 코드·문서·테스트·마이그레이션·에셋 변경

**통과 조건:** 변경 계약의 완료 조건을 코드 수준에서 충족하고 자체 검토 완료

## 4단계 — 검증과 리뷰

**목적:** 의도한 동작, 회귀 방지와 운영 안전성을 증명한다.

- 위험도에 맞는 [품질 게이트](QUALITY_GATES.md)를 실행한다.
- 요구사항 추적표에 구현·테스트 증거를 연결한다.
- 코드, 규칙, 보안·개인정보, 접근성, 성능, 에셋 품질을 검토한다.
- 실행하지 못한 검증은 이유와 위험을 명시한다.
- 치명적·높음 결함이 있으면 구현 단계로 돌아간다.

**산출물:** 명령 결과, 테스트 리포트, 리뷰 기록, 남은 위험

**통과 조건:** 필수 검증 통과, 차단 결함 0개, 필요한 독립 승인 완료

## 5단계 — 출시 준비

**목적:** 배포 단위를 재현 가능하고 되돌릴 수 있게 만든다.

- 릴리스 범위와 버전을 고정하고 `ReleaseNote.md`를 갱신한다.
- 환경변수, 마이그레이션 순서, 데이터 백업과 롤백을 확인한다.
- [출시 체크리스트](templates/RELEASE_CHECKLIST.md)를 작성한다.
- 스테이징에서 PC·모바일 2인 경기와 장애·복구 흐름을 확인한다.
- 배포·관찰·롤백 담당자를 지정한다.

**산출물:** 릴리스 후보, 체크리스트, 배포·롤백 계획

**통과 조건:** 출시 책임자가 증거와 남은 위험을 승인함

## 6단계 — 배포와 확인

**목적:** 통제된 방식으로 변경을 노출하고 즉시 이상을 감지한다.

- 승인된 커밋·이미지·마이그레이션만 배포한다.
- `/health`, 정적 웹, 매칭, 사전 로드, 경기 완료와 저장을 스모크 테스트한다.
- 오류율, 로드 실패, 취소율, DB 상태를 관찰한다.
- 중단 기준을 넘으면 새 변경을 멈추고 롤백한다.

**산출물:** 배포 기록, 스모크 결과, 모니터링 링크, 롤백 여부

**통과 조건:** 관찰 시간 동안 핵심 지표 정상, 배포 후 검증 완료

## 7단계 — 운영, 유지보수와 폐기

**목적:** 출시 후 품질을 유지하고 낡은 기능·데이터를 안전하게 정리한다.

- 결함, 신고, 문제별 지표와 의존성 보안 업데이트를 정기 검토한다.
- 장애는 [장애 보고서](templates/INCIDENT_REPORT.md)로 기록하고 재발 방지 작업을 추적한다.
- 규칙·기술 부채와 문서를 정기 감사한다.
- 호환 코드나 데이터 폐기는 사용 현황, 보존 기간, 백업과 롤백을 확인한 별도 변경으로 수행한다.
- 지원 종료는 사전 공지, 마이그레이션과 역사 기록을 남긴다.

**산출물:** 운영 리포트, 유지보수 백로그, 장애 회고, 폐기 기록

**통과 조건:** 종료가 아니라 반복 단계다. 다음 변경은 다시 0단계에서 시작한다.

## 변경 위험도

| 등급 | 예시 | 승인·검증 수준 |
|---|---|---|
| 낮음 | 오탈자, 링크, 동작 없는 문서 정리 | 자체 검토와 링크 확인 |
| 보통 | UI 개선, 독립 기능, 비파괴 리팩터링 | 변경 계약, 관련 자동 테스트, 동료 리뷰 |
| 높음 | 게임 규칙, 서버 판정, 공유 타입, DB, 보안, 라이선스, 배포 | 결정 기록, 독립 승인, 전체 품질 게이트, 롤백 리허설 |
| 긴급 | 운영 중 보안·데이터·서비스 장애 | 장애 책임자 승인, 최소 안전 수정, 배포 후 정식 회고 |

범위가 여러 등급에 걸치면 가장 높은 등급을 적용한다.

## 완료의 정의

작업은 코드가 동작할 때가 아니라 다음 조건을 모두 만족할 때 완료다.

- 승인된 문제와 범위를 해결했다.
- 정본·파생 문서·코드·테스트가 일치한다.
- 필수 자동·수동 검증의 증거가 있다.
- 보안·접근성·데이터·권리·운영 영향을 검토했다.
- 배포 또는 비활성화·롤백 방법이 있다.
- 남은 위험과 미확정 결정이 숨겨지지 않았다.
- 다른 사람이 인수인계 문서만으로 이어서 작업할 수 있다.
