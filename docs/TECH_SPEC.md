# 기술 설계서

## 1. 목적

실시간 1대1 경기에서 두 클라이언트가 같은 상태와 판정 결과를 공유하도록 구현 기준을 정의한다. 구체적인 프레임워크나 서비스 선택보다 책임과 데이터 흐름을 우선 확정한다.

## 2. 구성

- **웹 클라이언트:** 화면, 사용자 입력, 로컬 미리보기, 서버 상태 표현
- **애플리케이션 서버:** 사용자 세션, 매칭, 경기 생성, 일반 요청 처리
- **실시간 서버:** 상태 전이, 타이머, 진행도 전달, 연결 관리
- **저장소:** 사용자, 경기 결과, 신고, 이미지 및 제작 결과 보관
- **이미지 저장소:** 원본과 경기용 렌더링 결과 제공

MVP에서는 애플리케이션 서버와 실시간 서버를 하나의 서비스로 운영할 수 있다.

## 3. 책임 분리

### 클라이언트

- 제작 결과와 선택 위치를 서버가 이해할 수 있는 좌표로 변환한다.
- 입력에 대한 즉각적인 임시 피드백을 보여준다.
- 서버가 확정한 정답, 시간, 승패로 화면을 교정한다.
- 재접속 시 서버의 최신 스냅샷을 적용한다.

### 서버

- 매칭과 경기 상태의 최종 권한을 가진다.
- 차이점의 개수, 크기, 간격과 범위를 검증한다.
- 정답 및 오답, 힌트 사용, 종료 시각을 판정한다.
- 서버 시간을 기준으로 제한시간과 승자를 결정한다.
- 중복되거나 순서가 뒤바뀐 요청을 안전하게 처리한다.

## 4. 데이터 원칙

- 이미지 좌표는 화면 픽셀 대신 원본 너비와 높이를 기준으로 한 `0~1` 정규화 좌표를 사용한다.
- 정답 영역은 중심점과 반경 또는 경계 상자로 저장한다.
- 모든 경기 이벤트에는 경기 ID, 플레이어 ID, 상태 버전, 이벤트 ID, 서버 시각을 기록한다.
- 민감한 정답 좌표는 해당 문제를 푸는 플레이어에게 미리 전송하지 않는다.
- 제작 명령(`strokes`, `fill`)도 정답 위치와 동일한 정보이므로 풀이자에게 전송하지 않는다.
- 풀이 중 클라이언트가 받는 것은 렌더된 문제 이미지와, 자신이 이미 맞힌 위치뿐이다.
- 전체 정답은 경기가 `FINISHED`로 확정된 뒤에만 공개한다.
- 제작 명령과 정답 영역을 원본 이미지 버전과 함께 저장한다.

## 5. 실시간 통신

실시간 양방향 연결을 기본으로 하고, 초기 연결과 결과 조회 등은 일반 요청으로 분리할 수 있다.

주요 사건:

- 매칭 완료 및 경기 준비
- 플레이어 준비와 제작 제출
- 풀이 시작 및 서버 마감 시각 전달
- 위치 선택에 대한 정답·오답 응답
- 진행도 및 상대 진행도 변경
- 힌트 사용
- 연결 끊김과 복구
- 경기 종료 및 결과 확정

클라이언트 카운트다운은 서버 마감 시각을 표시하기 위한 보조 수단이며 판정 기준이 아니다.

## 6. 이미지 및 제작 처리

- 원본 이미지는 경기 시작 전에 양쪽에서 로드 가능한지 확인한다.
- 제작 단계의 미리보기는 빠른 반응을 위해 로컬에서 처리한다.
- **합성은 제작자 클라이언트가 수행하고, 결과 이미지를 제작 명령과 함께 서버로 제출한다.**
- 제출 시 서버가 제작 명령과 정답 영역을 검증하고, 이미지는 형식과 용량만 검증한다.
- **서버는 상대에게 결과 이미지만 전달한다.** 제작 명령과 정답 영역은 서버에 남는다.
- 서버가 픽셀을 다루지 않으므로 이미지 처리 라이브러리 의존성이 없다.
- 제한시간 안에 제작을 마치지 못하면 제작자 클라이언트가 마감 직전 자동 보충 후 제출한다.
- 원본 및 결과 이미지에는 직접 실행 가능한 콘텐츠를 포함하지 않는다.

## 7. 연결과 복구

- 연결이 끊기면 서버는 10초의 복귀 유예시간을 관리한다.
- 복귀한 클라이언트는 경기 상태, 남은 시간, 발견한 정답, 힌트 사용 여부를 다시 받는다.
- 유예시간이 지나면 서버가 기권 결과를 확정한다.
- 서버 장애로 판정을 신뢰할 수 없으면 경기를 취소한다.

## 8. 보안과 공정성

- 닉네임, 신고 설명 등 사용자 입력을 검증하고 출력 시 안전하게 처리한다.
- 경기 참여 권한과 요청 대상 플레이어를 매 요청마다 확인한다.
- 입력 빈도 제한으로 무작위 클릭과 서버 남용을 완화한다.
- 클라이언트가 보낸 시간, 점수, 정답 여부를 신뢰하지 않는다.
- 원본 및 이미지 에셋의 접근 권한과 라이선스를 관리한다.

## 9. 관측과 기록

- 경기 상태 전이와 취소 사유
- 매칭 및 각 단계의 소요 시간
- 연결 끊김과 재접속 결과
- 정답·오답·힌트 이벤트
- 이미지 처리 실패
- 서버가 거절한 입력과 그 사유

로그에는 불필요한 개인정보나 인증 정보를 남기지 않는다.

## 10. MVP 기술 선택

- **저장소 구조:** pnpm workspace 기반 모노레포
- **웹:** TypeScript, React 18, Vite, Tailwind CSS
- **서버:** Node.js LTS, TypeScript, Fastify
- **실시간 통신:** Socket.IO WebSocket과 자동 재연결
- **데이터베이스:** PostgreSQL
- **경기 중 임시 상태:** 단일 서버 메모리에서 시작하고 다중 서버 전환 시 Redis를 도입
- **이미지:** 원본은 객체 저장소에 보관하고 제작 명령을 구조화된 데이터로 저장
- **렌더링:** 제작자 클라이언트가 합성해 결과 이미지를 제출하고, 서버가 명령과 정답 영역을 검증
- **사용자 식별:** 서버 서명 게스트 세션과 사용자 지정 닉네임
- **테스트:** Vitest, React Testing Library, Playwright
- **배포:** 웹과 서버를 분리 배포하고 PostgreSQL과 객체 저장소는 관리형 서비스를 사용
- **배포 지역:** 초기 사용자를 고려해 서울 또는 가장 가까운 단일 리전

현재 `UI/` 시안은 React와 Vite 기반이므로 웹 기술은 유지한다. 다만 시안의 대규모 UI 의존성은 실제 사용 여부를 확인한 뒤 정리한다.

## 11. 확장 기준

다음 중 하나가 발생하면 경기 상태와 매칭을 Redis로 이동하고 서버를 수평 확장한다.

- 단일 서버의 동시 경기 처리 목표를 넘긴다.
- 무중단 배포 중 활성 경기를 유지해야 한다.
- 서로 다른 서버에 연결된 플레이어를 매칭해야 한다.

계정, 랭크, 결제, 사용자 이미지 업로드는 MVP 검증 이후 별도 보안·운영 설계를 거쳐 추가한다.
