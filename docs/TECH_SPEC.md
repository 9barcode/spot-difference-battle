# 기술 설계

> 문서 상태: CURRENT
> 기준일: 2026-08-07
> 게임 규칙은 `GAME_RULES.md`를 따른다.

## 구조

- 웹: React, 원본·변경본 표시, 터치·포인터 좌표 변환, 이미지 사전 로드
- 서버: Fastify·Socket.IO, 매칭, 문제 순서, 시간, 정답, 점수와 승패 판정
- 공유: 문제·상태·이벤트 타입과 게임 수치
- 게임 코어: 플레이어별 진행, 입력 잠금, 마감과 결과 판정
- 저장소: PostgreSQL 또는 로컬 메모리 구현

## 문제 카탈로그

장면 중심 카탈로그를 버전이 있는 문제 쌍 카탈로그로 전환한다.

각 문제는 `pairId`, 버전, 원본·변경본 자산 식별자, 이미지 크기·해시, 정답 영역 3개, 난이도, 라이선스와 활성 상태를 가진다. 정답 영역은 이미지 너비·높이 기준 `0~1` 정규화 좌표다.

이미지 파일은 CDN 또는 정적 자산으로 제공할 수 있지만 문제 순서와 정답은 서버가 관리한다. 클라이언트가 보낸 정답 여부·점수·문제 인덱스는 신뢰하지 않는다.

## 경기 계약

1. 매칭 시 서버가 두 플레이어와 문제 순서를 확정한다.
2. 양쪽이 첫 문제 로드 완료를 알린다.
3. 서버가 공통 시작·마감 시각을 배포한다.
4. 위치 선택에는 경기 ID, 상태 버전, 문제 인덱스, `pairId`와 정규화 좌표가 포함된다.
5. 서버가 정답·중복·오답·입력 잠금과 문제 완료를 판정한다.
6. 문제 완료 시 해당 플레이어의 다음 `pairId`와 진행을 내려준다.
7. 마감 시 서버가 동일한 결과 스냅샷을 양쪽에 보낸다.

## 상태와 데이터

기존 제작 제출·렌더 이미지·객체 효과·자동 보충 계약을 제거하고 `PRELOADING`, `COUNTDOWN`, `PLAYING`과 플레이어별 문제 인덱스를 추가한다.

활성 경기에는 문제 순서·버전, 시작·마감 시각, 플레이어별 발견 ID·오답·잠금 시각·연결 상태를 저장한다. 완료 경기에는 운영 감사를 위해 문제 버전과 최종 진행을 보존한다.

## 이미지 로드

- 첫 문제 로드 완료 전 시간을 시작하지 않는다.
- 현재 문제를 푸는 동안 다음 문제의 두 이미지를 미리 불러온다.
- 다음 문제 로드가 늦으면 플레이어 진행을 멈추고 공정성 정책에 따라 경기 취소 또는 양쪽 시간을 함께 보정해야 한다. MVP는 문제를 충분히 사전 로드해 이 상황을 오류로 처리한다.
- 원본과 변경본의 내용은 카운트다운 전 시각적으로 가린다.
- 웹은 원본·변경본에 같은 1~3배 배율과 정규화 이동량을 적용한다. 포인터 이동이 6px을 넘으면 드래그로 분류해 정답 요청을 보내지 않고, 선택 좌표는 변환된 이미지 경계 기준으로 다시 0~1 정규화한다.

## 보안과 동시성

- 정답 영역은 서버 전용이다.
- 상대의 발견 위치는 결과 전 전송하지 않는다.
- 상태·문제 인덱스·`pairId`가 다른 입력은 거절한다.
- 동일 정답 중복과 입력 잠금 중 요청은 무시한다.
- 서버 수신 시각으로 마감과 순서를 판정한다.
- 선택 요청에 속도 제한을 적용한다.

## 마이그레이션 영향

- 공유 역할·상태·이벤트·`GAME_CONFIG`
- `GameMatch`의 제작자/찾는 사람 판정
- 서버의 제출·힌트·문제 이미지 픽셀 검증 경로
- 웹 객체 편집기, 합성, 자동 제출과 관전 화면
- 활성 경기 저장 형식과 복구
- 모든 코어·서버·브라우저 테스트

기존 저장된 활성 경기는 새 상태로 안전하게 변환하기 어렵다. 배포 시 구형 활성 경기를 취소하거나 스키마 버전으로 분리하는 정책이 필요하다.
