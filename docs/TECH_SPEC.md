# 기술 설계서

> 문서 상태: CURRENT
>
> 기준일: 2026-07-31
> 각 절에서 `현재 구현`과 `목표`를 구분한다.
> 게임 규칙은 `GAME_RULES.md` 하나를 따르며 이 문서는 그 규칙을 구현하는 기술 계약만 설명한다.

## 1. 구성

현재 구현:

- pnpm workspace 모노레포
- 웹: TypeScript, React 18, Vite, Tailwind CSS
- 서버: Node.js, TypeScript, Fastify, Socket.IO
- 공유 계약: `packages/shared`
- 서버 권한 규칙: `packages/game-core`
- 저장소: PostgreSQL 또는 개발용 메모리 저장소
- 경기 중 상태: 단일 서버 메모리와 선택적 PostgreSQL `active_matches` 복구
- 원본 장면: 웹 번들에 포함된 로컬 이미지

목표:

- 웹과 서버 분리 배포
- 관리형 PostgreSQL
- 라이선스가 확인된 원본을 객체 저장소와 CDN에서 제공
- 다중 서버가 필요해지면 매칭과 활성 경기 상태를 Redis로 이동

## 2. 권한과 역할

클라이언트:

- 제작자의 객체 편집과 로컬 미리보기
- 정규화 좌표 생성
- PNG 문제 이미지 합성
- 서버 마감 시각 표시
- 서버 스냅샷 적용과 오래된 버전 무시

서버:

- 매칭 순서에 따른 제작자·찾는 사람 결정
- 상태 전이와 마감 시각
- 차이점 개수·영역·간격 검증
- 문제 이미지와 정답 좌표의 픽셀 변화 일치 검증
- 정답·오답·힌트·기권·승패 판정
- 참여 권한, 상태 버전과 입력 빈도 검사
- 경기·게스트·활성 상태·신고 저장

클라이언트의 시간, 점수와 정답 판정을 신뢰하지 않는다.

서버는 차이점 ID·좌표·반경·간격과 이미지 픽셀 변화에 더해 `objectEdit.objectId`가 해당 장면에 존재하는지, 객체가 중복됐는지, 효과가 허용 목록인지 검사한다. 웹 객체 마스크 ID와 공유 허용 목록의 일치 여부도 단위 테스트로 고정한다.

## 3. 데이터와 보안

- 좌표는 원본 너비·높이 기준 `0~1` 정규화 좌표다.
- 정답 영역은 중심점과 반경으로 저장한다.
- 풀이 중 찾는 사람에게는 렌더된 문제 이미지와 이미 맞힌 위치만 전달한다.
- 미발견 정답과 객체 편집 정보는 전달하지 않는다.
- 전체 정답은 `FINISHED`에서만 공개한다.
- 입력은 경기 ID, 기대 상태와 기대 상태 버전을 포함한다.
- 클라이언트는 같은 경기의 현재 버전 이하 스냅샷을 무시한다.

추측·힌트·기권·신고는 정확한 현재 버전을 요구한다. 제작 제출은 `EDITING` 상태를 유지하는 동안 연결 상태 변경으로 서버 버전이 앞선 경우에도 코어가 중복 제출과 마감을 다시 검사하도록 이전 버전을 허용한다.

현재 일반 경기 이벤트에는 별도 `eventId`와 `serverTime`이 없다. 서버 마감 시각 `deadlineMs`만 전달한다. 이벤트 추적 ID와 서버 수신 시각은 운영 관측 기능과 함께 추가해야 한다.

## 4. 이미지 처리

현재 흐름:

1. 제작자가 장면 객체 3개를 편집한다.
2. 클라이언트가 결과를 PNG data URL로 합성한다.
3. 서버 게임 코어가 PNG 형식과 최대 3MB 크기를 검사한다.
4. 서버가 원본·수정 이미지 픽셀을 비교해 제출한 정답 좌표에 실제 변화가 있는지 검사한다.
5. 서버는 찾는 사람에게 결과 이미지 한 장만 보낸다.

서버는 장면 ID별 원본 URL 카탈로그를 시작 시 읽어 메모리에 보관하고 경기 `imageId`에 해당하는 원본으로 제출 이미지를 검증한다. 현재 `prototype-room`과 `cartoon-laboratory` 원본이 등록돼 있으며, 공유 장면 ID를 추가하면 서버 원본 카탈로그도 함께 등록하도록 타입과 테스트가 강제한다.

현재 원본과 활성 문제 이미지는 객체 저장소를 사용하지 않는다. 진행 중 문제 이미지는 활성 경기 JSON 상태에 포함될 수 있으며 경기 종료 후 문제 이미지·제작 명령·정답 좌표는 영구 경기 테이블에 보관되지 않는다.

목표:

- 원본 장면을 객체 저장소/CDN에서 버전별 관리
- 신고 조사에 필요한 문제 이미지·정답·장면 버전을 보존 기간과 함께 저장
- 전송용 원본은 WebP 또는 AVIF를 사용하되 제작 제출 계약은 별도로 결정

## 5. 실시간 통신

주요 Socket.IO 사건:

- 세션 준비
- 매칭 참가·취소·성사
- 준비 완료
- 제작 제출
- 추측과 결과
- 힌트
- 기권
- 스냅샷
- 신고와 신고 결과

서버는 250ms 주기로 경기 마감을 확인한다. 추측과 힌트에는 기본 120ms 입력 간격 제한이 있다. 준비·제출·신고 등 모든 입력에 동일한 범용 제한이 적용되는 것은 아니다.

## 6. 연결과 복구

- 연결 상실 시 플레이어 상태를 `RECONNECTING`으로 바꾼다.
- 10초 안에 같은 게스트 토큰으로 복귀하면 최신 경기 스냅샷을 적용한다.
- 10초가 지나면 해당 플레이어를 기권시킨다.
- PostgreSQL이 설정된 경우 게스트와 활성 경기를 복구할 수 있다.
- PostgreSQL이 없으면 프로세스 재시작 시 메모리 상태는 복구되지 않는다.

게스트 토큰은 현재 임의 UUID bearer token이다. 문서에서 “서버 서명 토큰”으로 표현하지 않는다. 계정 또는 장기 인증을 도입할 때 서명·회전·만료 정책을 별도로 설계한다.

## 7. 저장

현재 PostgreSQL:

- `guest_sessions`: 게스트 토큰·닉네임
- `active_matches`: 진행 중 직렬화 상태
- `matches`: 종료 사유·승자·장면 ID·상태 버전
- `match_players`: 발견·오답·힌트·연결 상태
- `reports`: 신고 사유·설명·처리 상태

현재 완료 경기에는 문제 이미지, 전체 정답, 객체 편집과 단계별 시각이 저장되지 않는다. 따라서 불공정 신고 감사와 단계별 소요 시간 분석은 아직 불가능하다.

## 8. 오류와 취소

- 잘못된 입력은 해당 소켓에 오류 코드와 메시지를 반환한다.
- 정확한 버전이 필요한 입력의 오래된 상태는 `STALE_STATE`로 거절한다. 제작 제출에는 위의 제한적 동시성 예외가 있다.
- 문제 이미지와 정답 좌표가 맞지 않으면 제출을 거절한다.
- 저장 실패가 이미 확정된 서버 판정을 되돌리지는 않는다.
- 승패를 신뢰할 수 없는 경기 처리 오류는 `CANCELLED`로 끝낼 수 있다.

매칭 시간초과와 이미지 로드 준비 실패의 서버 취소 흐름은 아직 구현되지 않았다.

## 9. 관측

현재 Fastify 로거는 비활성화되어 있고 제품 지표·모니터링이 없다. 다음 항목을 개인정보 없이 구조화해 기록해야 한다.

- 매칭·상태 전이·단계별 소요 시간
- 취소·기권 사유
- 연결 상실·복귀 결과
- 정답·오답·힌트와 입력 거절
- 이미지 생성·검증 실패
- 저장 실패와 복구 결과

## 10. 확장 기준

다음 상황이 생기면 Redis와 다중 서버 구조를 검토한다.

- 단일 서버 동시 경기 목표 초과
- 무중단 배포 중 활성 경기 유지 필요
- 서로 다른 서버의 플레이어 매칭 필요

계정, 결제와 사용자 업로드는 MVP 이후 별도 보안 설계를 거친다.
