# 문서 운영 기준

> 문서 상태: CURRENT
> 기준일: 2026-08-31
> 책임 역할: 기술 문서 책임자

이 문서는 프로젝트 문서를 생성, 승인, 변경, 감사하고 폐기하는 방법을 정의한다. 문서 탐색의 시작점은 [문서 포털](README.md)이다.

## 1. 문서 원칙

1. **하나의 질문에는 하나의 정본**을 둔다.
2. 현재 구현, 확정 목표와 역사 기록을 섞지 않는다.
3. 중요한 규칙에는 구현과 테스트를 연결한다.
4. 코드와 문서의 충돌은 문서만 또는 코드만 몰래 고치지 않는다.
5. 숫자와 상태를 여러 문서에 복사할 때는 정본 링크와 동기화 책임을 명시한다.
6. 완료·검증·출시 표현은 증거가 있을 때만 사용한다.
7. 문서는 작업의 부산물이 아니라 완료 조건이다.

## 3. 문서 상태

모든 비역사 Markdown 문서는 제목 바로 아래에 상태, 기준일과 가능하면 책임 역할을 둔다.

- `CURRENT`: 현재 승인된 기준 또는 실제 상태
- `PROPOSED`: 검토 전 제안이며 구현 기준으로 사용 금지
- `TRANSITION`: 구·신 상태를 함께 운영하는 한시적 계약
- `HISTORICAL`: 당시 기록이며 현재 기준이 아님
- `ARCHIVED`: 더 이상 사용하지 않으며 대체 문서 링크가 있음

`DRAFT`, `APPROVED`, `IN_PROGRESS`, `VERIFIED` 같은 값은 변경 계약과 템플릿의 작업 상태에만 사용한다.

기준일은 마지막 편집일이 아니라 내용 전체를 코드·결정과 대조한 날짜다.

## 4. 책임 역할

| 역할 | 책임 |
|---|---|
| 제품 책임자 | 헌장, 범위, 규칙, 성공 지표와 출시 결정 |
| 기술 책임자 | 구조, 공유 계약, 데이터, 보안과 기술 결정 |
| QA 책임자 | 추적표, 테스트 계획, 품질 게이트와 검증 증거 |
| 콘텐츠 책임자 | 문제 난이도, 정답 영역, 권리·육안 QA |
| 운영 책임자 | 환경, 배포, 관측, 장애, 백업과 복구 |
| 문서 책임자 | 링크, 상태, 중복, 오래됨과 역사 분리 |

실제 담당자 이름은 공개 출시 전에 지정해야 한다. 한 사람이 여러 역할을 맡아도 승인 책임은 구분해 기록한다.

## 5. 변경 절차

### 규칙 또는 제품 범위

1. 변경 계약과 선택지를 작성한다.
2. 제품 책임자가 결정을 승인한다.
3. `PROJECT_CHARTER`, `MVP_DECISIONS`와 `GAME_RULES`를 먼저 수정한다.
4. 상태·모드·흐름·화면·기술·테스트·추적표·백로그를 동기화한다.
5. 코드·데이터·테스트를 구현한다.
6. 전체 품질 게이트 통과 후 관련 문서를 `CURRENT`로 확정한다.

### 기술·데이터·배포

1. 영향과 롤백을 포함한 변경 계약을 작성한다.
2. 고위험이면 결정 기록과 독립 승인을 받는다.
3. `TECH_SPEC`, `OPERATIONS`, `QUALITY_GATES`를 갱신한다.
4. 호환 가능한 순서로 구현·검증한다.
5. 릴리스 노트와 운영 증거를 남긴다.

### 작은 문서 수정

오탈자·깨진 링크처럼 의미가 바뀌지 않는 변경은 결정 기록 없이 수정할 수 있다. 규칙 의미, 상태 또는 완료 여부가 바뀌면 작은 수정이 아니다.

## 6. 중복과 충돌 처리

- 규칙 수치는 `GAME_RULES`와 공유 설정에만 권한이 있다.
- 파생 문서는 수치를 설명할 수 있지만 정본 링크를 포함한다.
- 코드와 정본이 다르면 배포 차단 결함으로 기록한다.
- 두 `CURRENT` 문서가 충돌하면 상위 정본을 확인하되, 의도가 불명확하면 `REVIEW_REQUIRED`에 등록한다.
- 같은 사실을 세 곳 이상 반복하면 표·링크 또는 추적표로 통합한다.

## 7. 문서 리뷰 체크리스트

- 제목, 상태, 기준일, 책임 역할이 적절한가?
- 현재, 제안, 역사 표현이 분리됐는가?
- 정본과 수치·용어·상태가 일치하는가?
- 코드·테스트·설정으로 사실을 확인했는가?
- 상대 링크가 존재하고 올바른 문서를 가리키는가?
- 완료되지 않은 항목이 완료처럼 쓰이지 않았는가?
- 사람 결정, 외부 검증과 위험이 숨겨지지 않았는가?
- 삭제·대체한 문서에 이동 경로가 있는가?

## 8. 정기 감사

- 코드·규칙 변경마다 관련 문서를 같은 변경에서 검토한다.
- 매 릴리스에 문서 포털, 추적표, 백로그, 검토 필요 항목과 릴리스 노트를 검토한다.
- 매월 `CURRENT` 문서의 기준일, 깨진 링크와 오래된 수치를 검색한다.
- 분기마다 정본 중복, 역사 문서 오용과 책임자 공백을 감사한다.

## 9. 역사와 폐기

날짜별 `CHANGES_*.md`는 당시 맥락을 보존한다. 현재 구현과 달라도 본문을 현재형으로 덮어쓰지 않는다. 누락된 상태 메타데이터나 깨진 링크만 고칠 수 있다.

문서를 폐기할 때는 `ARCHIVED`로 표시하고 대체 문서와 결정 이유를 남긴 뒤, 검색 결과와 외부 링크 영향을 확인한 후 별도 정리한다.
