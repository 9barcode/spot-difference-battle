# 운영과 유지보수 기준

> 문서 상태: CURRENT
> 기준일: 2026-08-31
> 책임 역할: 운영 책임자

이 문서는 스테이징부터 공개 서비스의 배포, 관측, 장애 대응, 데이터 보호와 장기 유지보수 기준을 정의한다. 현재 Render 실행 방법은 [배포 가이드](DEPLOYMENT.md)를 따른다.

## 1. 환경 구분

| 환경 | 목적 | 데이터 | 현재 상태 |
|---|---|---|---|
| 로컬 메모리 | 빠른 개발·단위 테스트 | 프로세스 종료 시 소멸 | 사용 가능 |
| 로컬 PostgreSQL | 마이그레이션·복구 통합 검증 | 개발 전용 | 사용 가능, 수동 실행 필요 |
| 스테이징 | 배포·PC/모바일 경기·롤백 검증 | 테스트 데이터 | Render 정의 존재, 실제 운영 상태 별도 확인 필요 |
| 프로덕션 | 공개 사용자 서비스 | 보호·백업 대상 | 환경·SLO·책임 체계 미확정 |

환경별 DB, 비밀정보와 URL을 공유하지 않는다. 운영 데이터를 로컬 또는 자동 테스트에 복사하지 않는다.

## 2. 릴리스 정책

- 버전은 Semantic Versioning을 사용한다.
- `main` 또는 승인된 출시 브랜치의 특정 커밋만 배포한다.
- 릴리스 범위는 `ReleaseNote.md`의 `Unreleased`에서 고정한다.
- DB·공유 계약·게임 규칙 변경은 별도 릴리스 위험으로 표시한다.
- 모든 릴리스는 [출시 체크리스트](templates/RELEASE_CHECKLIST.md), 배포 담당자와 롤백 지점을 가진다.
- 스테이징 통과 없이 프로덕션으로 직접 배포하지 않는다.

## 3. 배포 전 준비

1. 대상 커밋과 아티팩트를 고정한다.
2. `QUALITY_GATES.md`의 해당 게이트를 통과한다.
3. 환경변수와 비밀정보가 코드·로그·문서에 포함되지 않았는지 확인한다.
4. DB 변경 전 백업, 적용 순서, 구버전 호환성과 복원 방법을 확인한다.
5. 활성 문제의 버전·해시·권리·QA 상태를 고정한다.
6. 배포 관찰 담당자, 중단 기준과 롤백 담당자를 지정한다.

## 4. 배포 후 스모크 테스트

- `/health`가 서버와 DB 상태를 정상으로 반환한다.
- 정적 웹이 로드되고 Socket.IO 연결이 성립한다.
- PC·모바일 또는 두 독립 브라우저가 매칭된다.
- 같은 문제 버전, 사전 로드와 카운트다운을 거쳐 경기가 시작된다.
- 정답·오답·다음 문제·첫 완주 결과가 양쪽에 동기화된다.
- 기권 또는 재접속 흐름과 신고 저장이 동작한다.
- 로그에 토큰이나 정답 전체가 노출되지 않는다.

## 5. 관측 기준

현재 구현은 `/health`와 구조화된 일부 운영 로그를 제공하지만, 지표 저장·대시보드·알림은 미완료다. 공개 출시 전 최소 다음을 수집한다.

### 서비스

- 요청·Socket.IO 연결 성공률과 오류율
- 서버 응답시간과 이벤트 처리 지연
- 프로세스 재시작, 메모리·CPU와 DB 연결 상태
- 배포 버전별 오류 변화

### 경기

- 매칭 대기시간과 매칭 취소율
- READY·PRELOADING 취소율과 이미지 로드 실패율
- 경기 시작·완주·기권·재접속 성공률
- 종료 사유 분포와 양쪽 스냅샷 불일치

### 콘텐츠

- 문제별 노출·평균 풀이 시간·정답률·오답률
- 난이도별 완주율과 신고율
- 문제 버전별 품질 이상

알림 임계값과 SLO는 제품·운영 책임자 승인 후 기록한다.

## 6. 장애 대응

### 등급

- SEV-1: 보안 침해, 데이터 손실, 잘못된 승패가 광범위하거나 전면 장애
- SEV-2: 주요 기능·플랫폼 장애, 높은 경기 취소율, DB 불안정
- SEV-3: 우회 가능한 품질 저하 또는 일부 콘텐츠 문제

### 절차

1. 장애를 선언하고 한 명의 장애 지휘자를 지정한다.
2. 사용자·데이터 영향을 제한한다. 필요하면 매칭 또는 문제를 비활성화한다.
3. 배포 변화가 원인이면 우선 롤백한다.
4. 시각, 증상, 조치와 증거를 타임라인에 기록한다.
5. 복구 후 핵심 경기와 데이터 무결성을 검증한다.
6. SEV-1·2는 [장애 보고서](templates/INCIDENT_REPORT.md)와 재발 방지 작업을 남긴다.

긴급 수정도 사후에 정식 테스트·문서·결정 기록을 보완한다.

## 7. 데이터와 복구

- 마이그레이션은 번호순이며 이미 적용된 파일을 수정하지 않는다.
- 새 스키마는 가능하면 이전 애플리케이션이 읽을 수 있는 추가 방식으로 먼저 배포한다.
- 파괴적 열·테이블 제거는 사용 중단, 백필·검증, 보존 기간 경과 후 별도 릴리스로 한다.
- 완료 경기, 신고, 활성 경기와 게스트 세션의 보존 기간은 공개 출시 전에 확정한다.
- 백업 주기, RPO, RTO, 암호화와 접근 권한도 프로덕션 도입 전에 확정한다.
- 복원 테스트 없는 백업은 완료로 인정하지 않는다.

## 8. 롤백 원칙

- 애플리케이션은 직전 정상 이미지 또는 커밋으로 되돌린다.
- DB는 자동 하향 마이그레이션을 가정하지 않는다. 전진 호환 스키마로 앱 롤백을 우선 가능하게 한다.
- 문제 에셋은 파일 덮어쓰기가 아니라 버전 비활성화로 되돌린다.
- 롤백 후 `/health`, 매칭, 한 경기 완주와 DB 쓰기를 다시 확인한다.
- 롤백 원인과 후속 조치를 릴리스 기록에 남긴다.

## 9. 정기 유지보수

| 주기 | 작업 |
|---|---|
| 매 릴리스 | 변경 이력, 품질 게이트, 스모크, 롤백 지점 확인 |
| 매주 | 오류·취소·신고·로드 실패와 신규 높은 결함 검토 |
| 매월 | 의존성·취약점, DB 용량·백업 복원, 문서 오래됨 검토 |
| 분기 | 게임 밸런스·문제 품질·접근성·기기 매트릭스·SLO 검토 |
| 반기 | 데이터 보존, 권리 증빙, 호환 코드·기술 부채 폐기 검토 |

실제 주기는 운영 규모가 확정되면 조정하되 책임자와 다음 검토일을 반드시 지정한다.

## 10. 기능·데이터 폐기

1. 사용 현황과 의존 소비자를 확인한다.
2. 폐기 결정, 대체 경로와 일정을 승인받는다.
3. 쓰기를 먼저 중단하고 읽기 호환 기간을 둔다.
4. 데이터 백업과 복원 가능성을 확인한다.
5. 코드·타입·테스트·문서를 같은 변경에서 제거한다.
6. 역사 기록과 릴리스 노트에 남긴다.

현재 구형 장면 식별자와 중복 승패 함수 정리는 [검토 필요 항목](REVIEW_REQUIRED.md)에 등록돼 있다.
